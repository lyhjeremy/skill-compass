# Building SkillCompass

A resume can say "SQL" and "A/B testing" without anyone checking. SkillCompass is my attempt at a tool that does the checking for a data, analytics or finance professional, and answers three questions in under three minutes: where do I stand, what does the market want, and what should I do next. I set two constraints from the start. Nobody should have to sign up, and the infrastructure should cost $0 a month.

## How it is put together

The quiz loop makes no server calls. Questions ship as static JSON, and scoring, the knowledge-map coloring and the diagnosis all run in the browser, so the core of the product keeps working when the backend is down. The LLM endpoints power only the extras (gap reports, interviews and study guides).

I kept the calibration to plain math on purpose. Each item starts with an LLM-estimated difficulty prior *p*, which becomes an Elo rating through `R = 1500 − 400·log₁₀(p/(1−p))`. The session's ability rating updates after every answer with K = 48, and the percentile ranks the session's final rating against other sessions on the same subtopic. Each rule is a few lines of code that can be explained to the person being scored. The app's How it works page also documents a planned recalibration of items from logged responses, with a decaying K of 32/(1+n/40). The response log it needs is being collected; the update itself is not implemented, and item ratings still come from the priors.

The app is open about what it does not know. Percentiles appear only once a subtopic has 30 sessions, and until then it says "early data". Retakes draw unseen questions, and every question shows its public source.

The content pipeline assumes its own drafts are wrong. A generator writes questions in difficulty bands; a second, independent reviewer pass hunts for the failure modes in the item rubric (ambiguous keys, giveaway option lengths, trick phrasing) and repairs or rejects each one; and the plan is for a person to review everything before it counts. That last step has not happened yet: every bank in the repo is still marked "pending human review".

Privacy comes from the architecture. There are no accounts. All user state sits in localStorage (`sc_v1`) and can be exported or erased from the Progress page, and the only central record is an anonymous answer log. Resume text is used for one call and not stored.

## How the build went

The first pass, on 2026-07-05, covered Phase 0 and the core of Phase 1: the monorepo, a design system, the full quiz engine (placement routing, unseen-first draws, per-answer explanations and a reveal step), results with a rule-based diagnosis and an interactive knowledge map, a Progress page with export and erase, the Data Analyst track hub, a FastAPI skeleton and Dockerfile for Hugging Face Spaces, CI for the Pages and Space deploys, and the question pipeline producing the first six subtopics. I verified it end to end with a scripted click-through at 390px in both light and dark themes.

Two days later the catalog grew about tenfold. `content/catalog.json` became the single source of truth, at that point 160+ subtopics across 22 fields and 28 career tracks, referenced against Coursera, edX and Kaplan curricula. `build_manifest.py` works out live, partial or coming-soon status from whatever content exists, so subtopics, fields and tracks go live by themselves as their banks land. The generator became catalog-driven, variable-sized (popular topics aim for 30 questions), resumable and aware of rate limits, and I redesigned the Explore, Home and Track pages so they stay scannable at that size. The public beta went up at **lyhjeremy.github.io/skill-compass** on GitHub Pages, with SPA routing handled by a 404.html redirect.

Live percentiles arrived on 2026-07-08 (Phase 2). A FastAPI backend on a Hugging Face Space (Docker, free CPU) logs every completed session to Supabase (Postgres, free tier) and returns a percentile from a rolling 90-day window once a subtopic clears 30 sessions. The first snag was `supabase-py`, which mis-parsed Supabase's newer `sb_secret_...` key format as an invalid JWT before any request went out. I replaced it with a stdlib `urllib` PostgREST client of about 40 lines; that got around the bug and dropped a dependency.

The three LLM features (Phase 3) went in the same day, with Gemini's free tier wired up through the same stdlib REST pattern and one shared `gemini_generate()` helper. The resume gap report matches a pasted resume against a track's own curriculum. There is no job-postings corpus yet, so the report does not make up market statistics, and the text is used for one call and not stored. The mock interview capstone is a 6 to 8 turn text interview, pitched at the level the user has demonstrated, that asks follow-ups on thin answers and ends with a per-dimension scorecard. It is stateless (the frontend resends the transcript each turn), so there is no server-side session to leak. I checked that it does not rubber-stamp answers: a deliberately vague test answer was flagged and scored low across several follow-ups. The study guide generator produces a downloadable Markdown plan for a whole track from per-concept quiz results and, when present, the resume and interview context.

Testing against production turned up three bugs:

1. `gemini-2.0-flash` no longer had free-tier quota (a new key got a 429), so the default moved to `gemini-2.5-flash`.
2. `gemini-2.5-flash` spends its output-token budget on hidden "thinking" tokens by default. That truncated responses before the JSON or Markdown could finish, sometimes leaving no visible text at all. Setting `thinkingConfig.thinkingBudget: 0` fixed it; none of these calls needs chain-of-thought.
3. The Hugging Face deploy sometimes left the backend on a stale build even though the git push and the restart call both reported success. A plain `restart` can restart the existing container without rebuilding it; the call that rebuilds is `restart?factory=true`, which I found by reading `huggingface_hub`'s source because the REST docs do not cover it. I also changed the workflow from a fresh orphan `git init` and force-push on every run to an ordinary incremental commit on the Space's history, which has been more reliable.

## The outage the monitoring hid

On 2026-07-29 I found that the calibration store had been unreachable for an unknown stretch, and nothing had reported it. Three faults had stacked up.

The Supabase project had been paused for inactivity. A paused free project loses its DNS record, so the host answered NXDOMAIN and the Space logged `connection failed: [Errno -2] Name or service not known`. With no sessions being written, no subtopic could reach the 30-session threshold. The headline feature was frozen, and because the UI fell back to its "early data" label, everything looked normal.

The pause was caused by the keep-alive cron that was supposed to prevent it. It ran weekly against a 7-day inactivity threshold; with the guard interval equal to the threshold, a single delayed run trips the pause, and GitHub routinely drops scheduled runs on shared runners. The cron now runs `17 3 * * 1,4` (Monday and Thursday), which gives a 4-day nominal gap, 3 days of slack and two chances a week to fire. The general rule: a guard interval has to be shorter than the threshold it guards.

What hid the outage was `curl --fail` on `/api/aggregates`. That endpoint answers 200 with `{"status":"error", "detail": ...}` when the Supabase read fails, and `--fail` looks only at the status line, so three weekly runs passed straight through a total outage. `/api/health` has the same weakness; its top-level `"ok"` stays `true` while its `"supabase"` field is `false`. The cron now checks both response bodies and writes the result to `$GITHUB_STEP_SUMMARY`. I ran it against production in both states, and it went red at 18:25 with Supabase down and green at 22:30 with it back up.

Resuming the project from the Supabase dashboard brought everything back, with the pre-pause data intact; `/api/aggregates` returned `{"n":51,"window_days":90,"status":"live"}`. Recovery went through several stages: NXDOMAIN, then DNS within 30 seconds, then a Cloudflare 521 while the origin came up, then two or three minutes of PostgREST PGRST205 ("could not find the table 'public.sessions' in the schema cache") while the cache reloaded, and finally healthy. That PGRST205 stage looks like a missing migration, and it isn't one.

The same day I added a product overview page at `/overview/` (source `frontend/public/overview/index.html`). It leads with the gap between what a resume claims and what a check can prove, and it has eleven screenshots of the running app. On 2026-10-28 I rebuilt it in the portfolio's workshop style and added a working copy of the check: the real Model evaluation questions, the app's placement routing and its Elo update, running in the page with nothing stored. Two charts on it read straight from the repo: how far one answer moves a rating, over the 645 question priors, and live subtopics by field from the manifest. Its counts come from `content/catalog.json` and the question banks.

## Where it stands

SkillCompass is live at **lyhjeremy.github.io/skill-compass**. Four career tracks are fully live (Data Analyst, Data Scientist/ML, BI Analyst, Business/Product Analytics), covering 29 of the 385 catalog subtopics across 46 fields and 117 tracks, with 645 questions that have been through the draft and review passes; every bank is still marked pending human review. All three LLM features work end to end on a $0/month stack of GitHub Pages, a Hugging Face Space, the Supabase free tier and the Gemini free tier. Content for the rest of the catalog is still generating in the background. After the July 29 recovery the store held 51 sessions in the rolling 90-day window. By August the project had paused again (the keep-alive job has gone red on every run since 2026-08-06), so percentiles are off until it is resumed.

Still to build: a job-postings corpus and a market-demand gap analysis, which the resume feature leaves out for now; item recalibration from the logged responses; and content for the rest of the 385-subtopic catalog. The spec is `SKILLCOMPASS_SPEC.md` in the project folder.
